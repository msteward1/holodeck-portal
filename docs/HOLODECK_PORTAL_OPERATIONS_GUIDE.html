Getting started

Overview

What you install, what it talks to, and where its data lives.

The Holodeck Portal is a web application that drives the Holodeck PowerShell module on one or more Holodeck 9.x Holorouters, so users can deploy and manage nested VCF and VVF labs from a browser. The portal runs on its own: an appliance (or a container) next to your Holorouters, not on one of them. It never modifies Holodeck and never resets a Holorouter.

How it fits together

  Users (browser) ──HTTPS 443──► Holodeck Portal (appliance or container)
                                   nginx ─► portal (Node.js, SQLite) ─► PowerShell + PowerCLI
                                         │                        │
                       SSH 22 (portal key, pinned host keys)      HTTPS 443
                                         ▼                        ▼
              Holorouter (slot 1)   Holorouter (slot 2)   …   vCenter or ESXi host
              Holodeck · webtop     Holodeck · webtop         router VMs, nested lab hosts
              one lab               one lab
  • Every long operation is a job. Lab jobs run Holodeck on the lab's Holorouter over SSH; they keep running if the portal restarts, and the portal re-attaches to them.
  • Jobs that only talk to vCenter (reading inventory, deploying a Holorouter) run inside the portal with VMware PowerCLI. PowerCLI isn't shipped with the portal (Broadcom's licence doesn't allow it): the portal downloads it once, on first start (PowerCLI).
  • The portal keeps the master copy of every Holodeck configuration and copies it to a router before each job there.

Installation

Install the appliance

Deploy the OVA with vCenter, fill in its settings, and sign in.

Download

Download holodeck-portal-<version>.ova from the Releases page, with its SHA-256 checksum, and compare:

sha256sum holodeck-portal-<version>.ova

Deploy

  1. In the vSphere Client: Deploy OVF Template, choose the OVA, a name, a folder, a host or cluster and a datastore (thin provisioning is fine). On a standalone ESXi host, use the Host Client instead: Create / Register VM → Deploy a virtual machine from an OVF or OVA file; its Additional settings page holds the same settings.
  2. Map Management Network to the port group users and the Holorouters reach the portal on.
  3. Fill in the settings below and finish. Power the VM on.
Scripted deploymentWith ovftool, add --X:injectOvfEnv and one --prop:<name>=<value> per setting when deploying straight to an ESXi host; without it the settings don't reach the VM. PowerCLI's Get-OvfConfiguration needs vCenter.

First boot

The first boot applies the network, hostname, time servers and root password, gives the appliance its own SSH host keys, creates a temporary self-signed certificate for the portal name, starts the portal and creates admin with the password you gave. It takes a few minutes. Then open https://holodeck.example.com/ (your portal name), accept the certificate warning once, and sign in as admin.

Next: replace the certificate, set where updates come from if not GitHub (Updates), and continue with the administrator guide's first-time setup.

  2. Install a certificate for the new name (Certificate), and update the redirect URLs at your identity provider if you use single sign-on.
Installation

Install as a container

Run the same portal on a Docker host you manage.

The container includes nginx and PowerShell, and downloads VMware PowerCLI on first start (PowerCLI); nothing else is needed on the host. Updates are not one-click here: the portal shows the commands to run (see Updates).

Install

  1. From the Releases page, download holodeck-portal-<version>.hpupdate; from the repository, docker-compose.yml and the release/ folder (verify-release.sh and keys/).
  2. Verify and load the image: ./release/verify-release.sh holodeck-portal-<version>.hpupdate (checks the signature, digest and image ID; needs openssl 3, python3, sha256sum).
  3. Next to docker-compose.yml, create .env: 
    HP_HOSTNAME=holodeck.example.com
HP_PORTAL_IMAGE=holodeck-portal:<version>
  4. Start it: docker compose up -d. The portal listens on 80, 443 and 8441–8472 of the host.
  5. Create the first administrator (asks for the password twice): 
    docker exec -it holodeck-portal sh -c 'cd /opt/holodeck-portal/server && node dist/cli.js create-admin admin'

Data lives in two named volumes: portal-data (/var/lib/holodeck-portal: database, encryption key, SSH key, jobs) and portal-etc (/etc/holodeck-portal: certificate, gateway token). Back them up together (Backup).

Building the image yourself from the repository also works: docker compose build (with --build-arg HP_VERSION=<version> to set the version shown in About).

Installation

PowerCLI

VMware PowerCLI is downloaded on first start, because its licence doesn't allow shipping it with the portal.

The portal uses VMware PowerCLI for its own vCenter tasks: reading inventory for capacity profiles, and deploying, onboarding and deleting Holorouters. PowerCLI is Broadcom software whose licence doesn't allow redistributing it, so the portal doesn't include it. On first start it downloads the tested version (only the modules it needs, about 400 MB) from the PowerShell Gallery into its data folder, accepting Broadcom's licence on your behalf. It survives updates and is downloaded only once.

  • The download takes a minute or so. Until it has finished, those vCenter tasks are refused with "VMware PowerCLI is still being downloaded"; everything else works, including labs (Holodeck on the Holorouters uses their own PowerCLI).
  • If the download fails, administrators see a yellow notice on the dashboard with the reason, and the portal retries every 10 minutes. About shows PowerCLI's version and state.

Without internet access

On a machine with PowerShell 7 and internet access, save the modules, then copy them into the portal's data folder and restart the portal:

pwsh -c "Save-Module -Name VMware.VimAutomation.Vds -RequiredVersion 13.5.1.25718932 -Path ./Modules -AcceptLicense"
# appliance: copy ./Modules/* to /data/portal/lib/powershell/Modules/, then
systemctl restart holodeck-portal
# container: copy into the portal-data volume (powershell/Modules/), then docker restart holodeck-portal

Saving the modules this way also accepts Broadcom's PowerCLI licence. The version must match the one above (shown in About).

Configuration

Certificate

Replace the temporary self-signed certificate with one your browsers trust.

The portal starts with a self-signed certificate for its name. It is used on port 443 and on the webtop gateway ports. Manage it under Settings → Certificate, which shows the certificate in use (names, issuer, chain, expiry, SHA-256) and warns administrators 30 and 7 days before it expires.

With a certificate request (recommended)

  1. Generate CSR: the common name defaults to the portal's name. Add any other names users type (an alias, an IP address), and optionally organisation, unit, city, state, country and the key type (RSA 2048 by default). The private key is created on the portal and never leaves it; the current certificate stays in use.
  2. Download CSR (or Copy) and have your certificate authority sign it as a web server certificate.
  3. Install signed certificate: paste the certificate or choose the file (PEM, or DER .cer), including the intermediate certificates in any order.

The portal checks that the certificate matches the pending key, is valid now and names the portal (a switch allows another name), orders the chain, tests the web server configuration and switches over without a restart. Signed-in users stay signed in. Discard deletes a pending request and its key.

Other options

  • Upload certificate and key: for a certificate issued elsewhere. PEM certificate and key (the key may be encrypted; give its passphrase), or a PFX / PKCS#12 file with its password.
  • Regenerate self-signed: a new key and a certificate for the portal's name (plus extra names), valid 825 days.
  • Roll back to previous: the certificate in use before the last change. The current one becomes the previous, so a roll back can be undone.

Manually (recovery)

If the portal's pages can't be reached, replace the files directly. The certificate file holds the server certificate first, then the intermediates; the key must not be encrypted.

Form factorCertificateKey
Appliance/data/portal/etc/ssl/portal.crt/data/portal/etc/ssl/portal.key
ContainerIn the portal-etc volume: ssl/portal.crt and ssl/portal.key (/etc/holodeck-portal/ssl/ inside the container)

On the appliance, as root:

cp fullchain.pem /data/portal/etc/ssl/portal.crt
cp private.key   /data/portal/etc/ssl/portal.key
chmod 644 /data/portal/etc/ssl/portal.crt
chmod 600 /data/portal/etc/ssl/portal.key
systemctl restart holodeck-portal
openssl x509 -noout -subject -enddate -in /data/portal/etc/ssl/portal.crt

For a container, copy the files into the volume (for example docker cp fullchain.pem holodeck-portal:/etc/holodeck-portal/ssl/portal.crt, likewise the key) and run docker restart holodeck-portal. If both files are missing when the portal starts, it creates a new self-signed certificate.

Configuration

Updates

Check for new portal versions and install them from the About dialog.

Where updates come from

Releases are published on the project's GitHub repository. Each release is a container image plus a small manifest (version, the image's SHA-256, release notes) signed with the project's release key. The portal, the appliance's updater and, for containers, the release verifier all refuse a release that isn't signed by that key or whose image doesn't match the manifest, so a tampered download or a compromised release site can't install anything as long as you update through them.

Under Settings → Updates:

SettingDefaultNotes
Check for updates every dayOnAdministrators get a notification when a newer version appears. Turn off for sites that want no outbound calls; the portal sends nothing about itself either way.
Release sourceGitHubGitHub: repository owner/name. GitLab: server URL, group/project and an optional read-only access token (scope read_api), stored encrypted and sent only to that server, never through a redirect to another one. For mirrors and private forks.
Allow plain HTTPOffFor a lab GitLab without TLS. Off, an http:// GitLab is refused; on, the token travels unencrypted. Downloads never follow a redirect from HTTPS to HTTP.

Updating the appliance

  1. Open the user menu → About. The Updates panel shows the installed version and either You're up to date or the new version with its release notes. Check now asks right away.
  2. Click Update to <version>. The panel shows the download, then each step on the appliance: Verify the release, Load the new version, Back up the portal, Switch to the new version, Check the new version, Clean up.
  3. The portal restarts during the switch (usually a few seconds; the page reconnects by itself). When it's done the panel says Updated to <version>: click Reload.
  • Lab jobs running on Holorouters carry on during an update. An update is refused while a job runs inside the portal itself (such as a Holorouter deployment); try again when it has finished.
  • Before switching, the appliance backs up the database, encryption key, SSH key, trust files and settings to /data/backups/pre-<version>-<time> (the newest five are kept).
  • If the new version isn't healthy within five minutes, the appliance rolls back by itself: the previous version and the backed-up database. The About panel then explains what happened.
  • A release can require a minimum installed version; older portals then update in steps.

Without internet access

Download the release's holodeck-portal-<version>.hpupdate file elsewhere, then in About → Updates click Upload update file. It is checked exactly like a download (signature and image digest) and then offered with the same Update button.

Containers

A container has no updater beside it, so About shows the new version and these steps instead of a button. Download the release's holodeck-portal-<version>.hpupdate, then on the Docker host, next to docker-compose.yml:

docker cp holodeck-portal:/opt/holodeck-portal/release ./hp-release
./hp-release/verify-release.sh holodeck-portal-<version>.hpupdate
HP_PORTAL_IMAGE=holodeck-portal:<version> docker compose up -d

The verifier and the release key come out of the portal you already run, not from the download. It checks the signature, the image's size and SHA-256, loads it, and confirms Docker's image ID is the signed one (removing it otherwise); it needs openssl 3, python3 and sha256sum on the host. Never load a release image without it. Back up the volumes first (Backup); database changes apply when the new version starts. Set HP_PORTAL_IMAGE in .env to keep the choice.

Updates and Holodeck

Portal updates don't touch your Holorouters or Holodeck. Upgrade Holodeck on the routers separately (Maintenance).

Operations

Backup and restore

What to back up, how, and how to restore.

What to keep

ItemApplianceWhy
Database/data/portal/lib/portal.dbEverything the portal knows
Encryption key/data/portal/lib/secret.keyWithout it the stored secrets (lab and Holodeck configuration passwords, tokens) can't be read
SSH key and pinned host keys/data/portal/lib/ssh/Without it every Holorouter must be imported again
vCenter trust/data/portal/lib/trust/Approved vCenter certificate authorities
Settings and certificate/data/portal/etc/Certificate, gateway token

For a container these are the same files in the portal-data and portal-etc volumes. Every appliance update also makes a backup automatically (Updates).

Keep secret.key with the databaseThe two only work together. The backup contains secrets: keep it private.

Back up (appliance)

As root on the appliance; the portal keeps running:

B=/data/backups/manual-$(date +%Y%m%d-%H%M%S); mkdir -p -m 700 $B
docker exec holodeck-portal node -e "new (require('node:sqlite').DatabaseSync)('/var/lib/holodeck-portal/portal.db').exec(\"VACUUM INTO '/var/lib/holodeck-portal/portal-backup.db'\")"
mv /data/portal/lib/portal-backup.db $B/portal.db
cp -a /data/portal/lib/secret.key /data/portal/lib/ssh /data/portal/lib/trust /data/portal/etc $B/
tar -C /data/backups -czf $B.tgz $(basename $B) && rm -rf $B && chmod 600 $B.tgz

Copy the archive off the appliance. Installation files and the cached router OVA (/data/portal/lib/ova/) don't need backing up.

Restore (appliance)

systemctl stop holodeck-portal
tar -C /data/backups -xzf manual-YYYYMMDD-HHMMSS.tgz
R=/data/backups/manual-YYYYMMDD-HHMMSS
rm -f /data/portal/lib/portal.db /data/portal/lib/portal.db-wal /data/portal/lib/portal.db-shm
cp $R/portal.db $R/secret.key /data/portal/lib/
cp -a $R/ssh $R/trust /data/portal/lib/
cp -a $R/etc/. /data/portal/etc/
systemctl start holodeck-portal

Restoring an automatic update backup works the same way: its folder holds portal.db (with its -wal file), secret.key, ssh, trust and etc. Labs changed after the backup may be out of date: Refresh them, or Forget lab those that no longer exist.

Moving to a new appliance

Deploy the new appliance, back up the old one, stop the old portal, restore the backup on the new one (keeping the new appliance's own certificate if you prefer: skip etc), and point the portal's DNS name at the new address. Sign in with your existing accounts afterwards.

Operations

Maintenance

Housekeeping the portal does by itself, routine checks, and Holodeck upgrades.

Automatic

  • Hourly: expired sign-in sessions are removed; job folders of jobs finished more than 90 days ago are deleted (the job list keeps them); audit entries older than the retention period (Settings → General, default 365 days) are deleted.
  • Every 5 minutes (Settings → Holorouters → Health check): every router is checked over SSH, its installation files are re-read, and webtop activity is counted for the idle policy.
  • Daily: a check for portal updates (if on); the certificate's expiry is checked hourly.

Routine

WhenTask
DailyDashboard: failed labs, prompts waiting, expired leases. Holorouters: all Ready.
WeeklyBack up. Check free space on /data (appliance) and /holodeck-runtime on the routers. Review failed sign-ins and credential views in the audit log.
MonthlyInstall portal updates; clear old remote job folders on the routers; unstage versions nobody uses.
# On each Holorouter: remote job folders older than 90 days
find /var/lib/holodeck-portal-agent/jobs -mindepth 1 -maxdepth 1 -mtime +90 -exec rm -rf {} +
# On the appliance: free space and the certificate
df -h /data
openssl x509 -enddate -noout -in /data/portal/etc/ssl/portal.crt

Health checks (appliance)

systemctl is-active holodeck-portal holodeck-updater.path docker
curl -s http://127.0.0.1:3080/api/health        # {"ok":true,"version":"…"}
docker ps --filter name=holodeck-portal           # Up … (healthy)
docker logs --tail 100 holodeck-portal            # the portal's log
journalctl -u holodeck-updater -n 50              # the last update

Holodeck upgrades

Upgrade Holodeck on every router, one router at a time while it has no lab. Router checks warn when a router's Holodeck version differs from the one most routers run. After upgrading, check the router's installation files (a new Holodeck may expect different file names) and run a test deployment.
