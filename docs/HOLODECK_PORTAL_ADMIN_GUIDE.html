Getting started

Overview

What administrators look after, how the pieces fit, and where to start.

The Holodeck Portal drives the Holodeck PowerShell module on a fleet of Holodeck 9.x Holorouters so users can deploy and manage nested VCF and VVF labs without a shell. Each Holorouter hosts one lab; capacity grows by adding routers. The portal never modifies Holodeck itself and never resets a Holorouter.

Architecture

  Users (browser) ──HTTPS 443──► Holodeck Portal (appliance or container: nginx, Node.js, SQLite, PowerCLI)
                                      │                                  │
                 SSH (portal key, pinned host keys)                  HTTPS (PowerCLI)
                                      ▼                                  ▼
        Holorouter slot 1    Holorouter slot 2    …            vCenter or ESXi host
        Holodeck · webtop    Holodeck · webtop                 router VMs, nested lab hosts
        DNS · DHCP · lab 1   DNS · DHCP · lab 2
  • Every long operation is a job: a list of Holodeck commands with its output streamed to the browser. Lab jobs run on the lab's Holorouter, in their own systemd unit there; the portal copies its runner and the Holodeck configuration over SSH first.
  • The portal holds the master copy of every Holodeck configuration (encrypted, since it contains the target's credentials). Configuration work (creating one, changing settings, prechecks) runs on a free Holorouter, and the result comes back to the portal.
  • Tasks that only talk to vCenter (reading inventory, deploying and onboarding a Holorouter) run inside the portal with PowerCLI.
  • Installing, updating and backing up the portal itself are in the Installation and operations guide.

Getting started

First-time setup

A checklist that takes a freshly installed portal to its first user lab.

  1. Certificate: replace the temporary self-signed certificate under Settings → Certificate (how).
  2. Network pool: under Settings → Network pool, list the VLANs and networks your site already uses (blocked lists) and check the slots shown. Do this before the first router (Network pool and VLANs).
  3. Webtop password: Settings → Holorouters; and the Holorouter OVA URL and its SHA-256 if the portal will deploy routers.
  4. First Holorouter: deploy the Holorouter OVA in vCenter yourself, then Holorouters → Import existing with Capacity profile set to None (Holorouters). Configurations are created on a Holorouter, so the portal needs this one before anything else.
  5. Configuration: Configurations → New configuration (target vCenter or ESXi host and its credentials); set entitlements, deploy defaults and depot access; optionally run a precheck (Configurations).
  6. Installation files: put each VCF version's files on one router, then stage them to the others (Installation files).
  7. Settings: portal name, maximum labs and quotas, leases, idle labs (Settings).
  8. Sign-in: create local users or configure OpenID Connect / SAML (Users, Single sign-on).
  9. Test: deploy a small VVF lab yourself, open its webtop and credentials, shut it down, power it on and remove it.
  10. More capacity: create a capacity profile for the configuration, Deploy new routers with it (or import more), stage versions on them, and raise Maximum labs.
Labs and users

Configurations

A configuration wraps one Holodeck configuration (target vCenter or ESXi host, placement, depot) and decides who may deploy from it and with which defaults.

The Configurations page

Cards show each configuration: name, Holodeck config ID, target, cluster, datastore and trunk port group, a vCenter or ESXi host badge for the target type (Target unknown until the portal has connected to it), Published or Disabled, who may use it, how many labs use it, and an amber "unmanaged instance on <router>" tag when a router has a Holodeck instance bound to it that no portal lab owns. Below is a table of Holodeck configurations not yet in the portal: configurations the portal holds but that aren't registered.

Adding a configuration

  • New configuration: name, description, target host (vCenter or ESXi FQDN/IP), username and password. The portal runs New-HoloDeckConfig on a free Holorouter, keeps the result and registers it. The password goes to Holodeck and the portal's encrypted store only, and is masked in the job output. Set placement and depot details afterwards.
  • Register a configuration from the table: give it a display name and description.

Configuration jobs (new, Holodeck settings, precheck) run on a router that is ready and idle, preferring the lowest slot; they need at least one Holorouter. Before every job on a router, the portal copies the configuration there, keeping that router's own instance binding and network status.

Configurations and Holorouters

  • A Holorouter with a capacity profile serves only the profile's configuration: its networks and placement belong to that target. Its labs use the profile's cluster, datastore, resource pool and site A trunk port group.
  • A Holorouter without a profile serves any configuration, and its labs use the configuration's placement.
  • On the deploy page, a configuration whose routers are all in use is greyed out ("all Holorouters in use"); one that no router serves is hidden from users and shown greyed to administrators.

Rules

  • You can't disable, demote or delete your own account.
  • Users who have ever owned a lab can't be deleted (the lab history keeps the owner). Disable them, or reassign their labs first.
  • Administrators aren't limited by the maximum lease and can deploy from any configuration, on behalf of other users and on a chosen Holorouter.

Recovering access from the shell

As root on the appliance (or on the Docker host):

docker exec -it holodeck-portal sh -c 'cd /opt/holodeck-portal/server && node dist/cli.js reset-password admin'
docker exec -it holodeck-portal sh -c 'cd /opt/holodeck-portal/server && node dist/cli.js create-admin admin2 First Last'

Both commands ask for the password twice without showing it.

Labs and users

Single sign-on

Let users sign in with OpenID Connect or SAML 2.0, map their groups to portal roles and create their accounts automatically.

Configure sign-in under Settings, in the Local accounts, OpenID Connect and SAML 2.0 sections. The redirect and metadata URLs to give your identity provider are shown there; they are built from HP_PUBLIC_URL.

Role mapping (both protocols)

  • Member of an admin group → Administrator.
  • Member of a user group, or no user groups configured → User.
  • Otherwise the sign-in is refused: "Your account is not in a group that is allowed to use this portal."

Role, email and names are updated from the identity provider at every sign-in. With Create portal accounts on first sign-in off, only pre-registered users can sign in. A username that already belongs to an account of another sign-in type is refused rather than merged.

Account linking

An SSO account is tied to the identity provider's permanent identifier for the person (the OIDC sub, or the SAML NameID), not to the username. The first sign-in links a pre-registered or new account. After that, a sign-in that presents the same username with a different identifier is refused ("linked to a different identity") and recorded in the audit log as auth.sso.identity-conflict, because usernames can be renamed or reused at the identity provider. If the change is legitimate (a new provider, a re-created directory account), use Unlink SSO identity on the user.

Allow local username/password sign-in can be turned off for users once SSO works. Local administrators can still sign in through the Administrator sign-in link on the login page, so a broken identity provider can't lock you out.

Expired and failed labs

  • Expired: the lab is powered off and stays until you renew or remove it. The dashboard's Leases expiring tile counts expired labs.
  • Failed: read the job log; fix the cause; Retry deployment (Holodeck resumes) or remove. Export diagnostics collects Holodeck's error stack.

How deployments are placed

A lab goes to a Holorouter that is Ready, whose slot is inside the network pool, has no lab, isn't staging files, has the lab's version staged, and serves the lab's configuration (its capacity profile is for that configuration, or it has no profile). The lowest such slot wins unless you pin a router. The number of labs is also capped by Maximum labs.

Lab names

  • A blank instance ID becomes s plus the slot's two digits: a lab on slot 6 is s06, so its VM names start with s06-. If that ID is taken (someone chose it by hand for another lab), a letter is added: s06b.
  • The lab's DNS domain comes from the Per-lab DNS domain template, by default lab{slot}.vcf.lab (lab06.vcf.lab). Each slot hosts one lab at a time, so these names never clash between running labs.

Network pool and VLANs

How the portal turns the pool settings into each slot's networks and VLANs, and what the vSphere network must carry.

The formula

Slot n (starting at 1) reserves two consecutive /20 networks: second octet start + (n−1)×2 for site A (deployed) and the next one for site B (reserved for dual-site). Each site's VLAN range starts at second octet × multiplier and uses 32 VLANs. The number of slots is floor((end − start + 1) / 2).

SlotSite AVLANsSite B (reserved)VLANs
110.1.0.0/20100–13110.2.0.0/20200–231
210.3.0.0/20300–33110.4.0.0/20400–431
310.5.0.0/20500–53110.6.0.0/20600–631
410.7.0.0/20700–73110.8.0.0/20800–831
510.9.0.0/20900–93110.10.0.0/201000–1031

The settings page validates the pool: every VLAN must be ≤ 4094 and the multiplier must be at least 32 so ranges don't overlap. Each Holorouter owns one slot; a slot without a router can't host a lab.

Blocked VLANs and networks

A lab must never use addresses or VLANs that exist elsewhere on your network: Holodeck configures them on the lab's Holorouter, and an overlap with the management network cuts the router off (and could disturb the real network). List what your site uses:

  • Blocked VLANs: single VLANs or ranges, e.g. 1210-1218, 1500. Each lab site uses 32 VLANs from its start (second octet × multiplier), so 10.11 means VLANs 1100–1131.
  • Blocked networks: networks or addresses, e.g. 192.0.2.0/24.

A pool range (a slot's two /20s) that touches any of them is skipped, and slot numbering continues with the next range. With the default pool and 1210-1218 blocked, slots 1–5 stay on 10.1–10.10 and slot 6 becomes 10.13.0.0/20 (VLANs 1300+), provided the pool end is at least 14. The settings page lists the usable slots and the skipped ranges with the reason.

Address guard. The portal also knows the management networks it can see: its own network and every router's management address. A slot overlapping one is shown as a problem until you block it, and the portal won't give such a slot to a new router or deploy a lab into it. A change that would move the networks of a slot a router already uses is refused: detach or forget that router first.

vSphere requirements

  • The trunk port group a router's eth1 (site A) uses must carry that slot's site A VLAN range; eth2 (site B) its site B range.
  • Holodeck requires promiscuous mode, MAC address changes and forged transmits on those port groups.
  • The lab's nested ESX hosts use the same site A trunk port group as their router.
Untagged traffic and DHCPHolodeck serves DHCP on its untagged Untagged-HOL network on eth1. Routers whose eth1 shares one port group share that untagged segment, and every router's trunk sees every VLAN on it. Giving each slot its own trunk port group, carrying only that slot's VLAN range, keeps labs apart.

Per-lab DNS domain

Each lab is deployed with -DNSDomain from the template: {slot} becomes the lab's slot as two digits and {instance} its instance ID. The default lab{slot}.vcf.lab gives lab06.vcf.lab on slot 6. A slot hosts one lab at a time, so slot-based names never clash between running labs, and a router's labs always get the same domain. Other placeholders are refused. Users can't change the domain; administrators can override it per lab on the deploy form. A changed template applies to new labs.

Platform

Capacity profiles

A capacity profile says where in vCenter, or on which standalone ESXi host, a Holorouter VM goes and where its lab's nested hosts are placed.

Creating a profile

  1. Capacity profiles → New profile. Give it a name.
  2. Choose the vCenter (from configuration): the portal connects with that configuration's target credentials.
  3. Click Read inventory (later Refresh inventory). A short job reads datacenters, clusters, resource pools, VM folders, datastores (with free space) and networks; the result is kept until you refresh it.
  4. Pick Datacenter, Cluster, optional Resource pool and VM folder (for router VMs), Datastore, Management network (the router's eth0; needs outbound access), Trunk port group — site A (router eth1 and the lab's nested hosts) and Trunk port group — site B (router eth2, for dual-site later). Save.

The site A trunk can't be the management network. Distributed port groups are marked (dvPG).

vCenter certificate

The profile list shows Certificate approved or Certificate not approved under the vCenter. Click it to see the certificate vCenter presents now (subject, issuer, expiry, SHA-256). Compare the SHA-256 with the one in the vSphere Client or from your vCenter administrator, then click Approve this certificate.

  • With an approval, Deploy new checks that vCenter still presents that certificate before connecting. If the certificate has changed, the job stops before anything is deployed; review and approve the new certificate if the change is expected (for example a renewal).
  • Without an approval, Deploy new is refused for that profile (the deploy dialog says so). Lab deployments are not affected.
  • Approving also saves the certificate authority that signed vCenter's certificate (vCenter publishes it at /certs/download.zip; the portal keeps it only if it really signed the approved certificate). The deploy job then signs in to vCenter, which sends the vCenter credentials, with PowerCLI refusing any certificate that doesn't chain to that authority or doesn't name the host. If no authority could be saved, the dialog offers Approve again; until then deployments use the fingerprint check alone, with a note in the job log.
  • Changing a profile's vCenter configuration clears its approval.

Strict sign-in applies to vCenter targets only: standalone ESXi certificates rarely carry the host's name, so ESXi targets keep the approved-fingerprint check. Holodeck's own connections to vCenter (lab deployments, power, removal) use Holodeck's PowerCLI setting, which ignores certificate errors; the portal does not change it.

Standalone ESXi hosts

Holodeck can target a single ESXi host instead of a vCenter, and so can a capacity profile. Choose a configuration whose target is an ESXi host and read its inventory: the host appears in place of a cluster ((standalone host)), with its resource pools, datastores and port groups. There are no VM folders.

  • One host, one profile. A site with several standalone hosts uses one Holodeck configuration and one capacity profile per host; you choose the host by choosing the profile.
  • Port groups. Create the trunk port groups yourself on the host's standard switch: VLAN 4095, with promiscuous mode, MAC address changes and forged transmits set to Accept.
  • Certificate. Approve the host's certificate like a vCenter's. ESXi's default certificate is self-signed and often issued to localhost.localdomain, so deployments check the approved fingerprint; the stricter certificate-authority check is for vCenter only.
  • Licence. Deploying a router writes through the host's API. Evaluation mode allows that. The free ESXi licence, or an evaluation that has ended, does not: the profile and the deploy dialog say so, and Deploy new is refused. Deploy the Holorouter OVA on the host yourself (ESXi Host Client), then add it with Import existing. Labs work either way.
  • Labs. Holodeck places a lab's nested hosts on the profile's datastore and trunk port group; cluster and resource pool don't apply.
  • Nested ESXi hosts. If the target ESXi host is itself a VM, the port groups its uplinks use on the outer vSphere need MAC learning (or promiscuous mode) plus forged transmits and MAC address changes set to Accept. Otherwise the outer switch drops the router's traffic: it boots, but its address doesn't answer. Also match the MTU: Holorouters use MTU 8000 on eth0, so the nested host's vSwitches (and the outer switches) need at least that, typically 9000. With a 1500 vSwitch, ping works but SSH stalls during its key exchange and the deployment stops with an MTU hint.
  • Router settings. A standalone host has no vApp settings, so the portal deploys the router powered off, writes its settings (address, hostname, root password) into the VM's guestinfo.ovfEnv, powers it on, and removes them again after onboarding. When you deploy a router by hand on a standalone host (for Import existing), check that it comes up on the address you entered; if it takes a DHCP address instead, its settings didn't reach it.
  • ESXi hosts managed by a vCenter. Use the vCenter as the target; vCenter usually blocks deployments made directly on a host it manages.

Using profiles

  • A profile belongs to one configuration (its vCenter or ESXi target). A router with the profile takes only that configuration's labs; give each configuration at least one router.
  • Deployed routers always have a profile. An imported router may have none: it then takes any configuration's labs, which use the configuration's own placement.
  • A router's profile can be changed on its page only while it has no lab.
  • A profile used by routers can't be deleted.
  • The trunk port groups must carry the VLANs of every slot whose router uses the profile.

Holorouters

Each Holorouter owns one network slot and runs one lab. Add routers to add lab capacity.

The Holorouters page

One card per router: name and address, status, slot and network, its lab or Free, profile (or Configuration placement without one), Holodeck version, Staged versions (or "None — labs can't be placed here"), and the check results. Deploy a new Holorouter

Deploy new deploys the Holorouter OVA from Holorouter OVA URL into the vCenter or ESXi host of a capacity profile.

Before anything starts, the portal needs an OVA it can authenticate (see OVA SHA-256 in Settings) and an approved certificate on the profile (see Capacity profiles). The job runs in the portal and:

  1. downloads the OVA into the portal's cache (it needs the OVA's size plus 2 GB free) and checks its SHA-256;
  2. checks that vCenter presents the approved certificate, signs in (strictly, where enabled) and deploys the VM with PowerCLI, then powers it on. On a standalone ESXi host the VM is deployed powered off, its NICs and settings are written, then it is powered on;
  3. waits for first boot (SSH, then the webtop answering, up to 45 minutes);
  4. onboards the router: installs the portal's SSH key and gives the router its own SSH host keys (below), pins the new key and runs the router checks.

Onboarding and SSH host keys

Every Holorouter OVA ships with the same SSH host keys, so a shipped key can't identify a router: anyone with the OVA has its private key. The portal therefore replaces them during onboarding.

  • Through vCenter (preferred). The portal asks vCenter, over the approved certificate, to run the onboarding inside the new VM through VMware Tools: it installs the portal's key, generates new host keys and reports the new fingerprint, which the portal pins. The root password goes only to vCenter; it never travels over SSH. The job log says The root password was not sent over SSH.
  • With your confirmation (fallback). This needs the Guest operations privileges (modify, program execution, queries) for the vCenter account of the Holodeck configuration. They are optional: without them the job pauses with a prompt showing the fingerprint the router offers. Open the VM's console in vCenter, sign in as root, run the command below and answer yes if it matches. The portal then installs its key with the root password over SSH, checked against that key, and replaces the host keys straight away.
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

New host keys are prepared in a temporary folder, checked by sshd -t (the old ones come back if that fails) and loaded with a reload, so nothing that is connected is interrupted.

Import an existing Holorouter

Import existing: hostname or IP, root password (used once, not stored), optional display name (defaults to the router's address), capacity profile and versions to stage. The profile must match the port groups the router's NICs use; with None the router serves any configuration, and its labs use the configuration's placement (this is how the first router is added). The portal installs its key, then checks the router.

  1. Enter the address and click Scan host key. The dialog shows the router's SSH host key fingerprint, e.g. ssh-ed25519 SHA256:….
  2. On the router's console, run the command below and compare. Confirm with This is the fingerprint the router shows; Import stays disabled until you do.
  3. The import job pins that key before connecting. If the router presents any other key, the job fails before the password is sent.

The router page

  • Overview: slot, site A and B networks, lab, Holodeck version, last seen, the pinned SSH host key, size (vCPU, memory, free disk), Kubernetes pods, NICs, blockers and warnings.
  • Placement: the capacity profile (changeable while the router has no lab), and Webtop access while the webtop gateway is on.
  • Idle labs: follow the default (Settings → Leases), this router's own stages, or never (see Leases and idle labs). Saving starts a fresh idle period for the router's lab.
  • SSH host key: if another router presents the same key, the page says so and offers Renew SSH host key. It runs a short job that gives the router its own keys; labs and open sessions on the router carry on.
  • Installation files: see Installation files.
  • Services: the Holorouter's services (name, FQDN, address) and a link to its Technitium DNS. Holodeck's own DNS cmdlets don't work on 9.1 Holorouters, so manage extra DNS records in Technitium.

  • Header buttons: Webtop, Check now, and the pencil icon to rename the router.

Webtop gateway

On by default, with routers Through the portal only: users click Webtop and are signed in, and nobody needs the shared webtop password. Change the default in Settings → Holorouters, or a router's mode under Webtop access on its page. With the gateway off, or a router on Direct, users open http://<router>:30000 and type the shared login: simpler for a closed lab network, but every lab owner then knows the login and it travels unencrypted.

While the default is Through the portal only, administrators see a yellow notice on the dashboard explaining it (and reminding them to set the webtop password if it's missing). Dismiss hides it until the next sign-in; Don't show again is remembered on the account.

Through the portal onlyAs aboveThe portal closes the router's webtop ports (30000, 30001) and its web services (80, 443) on the management interface, and re-checks this at every health check.
  • Each router has its own portal port, so each webtop is a separate site in the browser: one router's desktop can't reach the portal pages or another router's desktop.
  • The portal reaches each router's webtop through a relay over its SSH connection, so the desktop and its login don't cross the management network unencrypted.

Platform

Installation files

Holodeck needs the ESX installer ISO and the VCF Installer or Cloud Builder OVA for each version. Put them on any one router; the portal copies them to the others.

Where the files go

On a Holorouter, each version has its own folder, for example /holodeck-runtime/bin/9.1.0.0/. Each folder needs two files:

  • the ESX installer ISO, and
  • the VCF Installer OVA (VCF 9.x) or Cloud Builder OVA (VCF 5.x).

Download them from the Broadcom support portal and copy them to one router. They must have exactly the names Holodeck lists in its bill of materials, /holodeck-runtime/templates/bom.json. Holodeck's precheck refuses other file names, including newer patch builds, so don't rename different builds.

jq 'to_entries[] | {version: .key, esx: .value.esx, installer: (.value["vcf-installer"] // .value["cloud-builder"])}' /holodeck-runtime/templates/bom.json

On a router's page

Holorouters → a router → Installation files lists each version Holodeck knows, newest first:

  • a staged version shows its files: both accepted files are present on this router;
  • otherwise, the size to copy and the router it would come from, or "No other Holorouter has it" with where to put the files;
  • a partial or different copy is flagged, and files Holodeck's precheck won't accept are listed.

Staging

  1. Tick the versions to copy and click Stage selected.
  2. Follow the job: it checks free space (what's needed plus 5 GB), then streams each file from the source router to this one through the portal, with progress lines (percentage, rate, time left), verifies the SHA-256 on both routers, and only then gives the file its real name.

The source is any healthy router with a complete copy, preferring one with the same Holodeck version (its bill of materials decides the file names), then the lowest slot. You can also choose versions in the Deploy new and Import existing dialogs; they are copied once the new router passes its checks.

  • An interrupted copy resumes where it stopped when you stage again.
  • While a router is staging, it doesn't take new labs.
  • Labs are only placed on routers that have their version staged; the deploy form greys out versions no free router has.
  • The delete button next to a staged version removes its files from that router (not while a lab of that version runs there).
  • Files added or removed by hand are picked up at the next health check or when you open the router's page.
Copy speedCopies run over SSH from the source router, through the portal, to the target, so the network between the portal and the routers sets the pace. A VCF version's files add up to tens of GB.

Leases and idle labs

How leases and the idle policy run, and which notifications users and administrators receive.

The lease check

Every minute the portal looks at every lab that is queued, deploying, ready or failed:

  • When the remaining time passes the first, then the second warning lead time, the owner gets one warning each (a lease that starts inside both windows warns once).
  • At expiry the lab is marked expired, the owner gets an error notification and every other administrator a warning, and once the lab is ready and idle it is shut down (audited as "Lease expired"). Labs still deploying are shut down after they finish. Nothing is deleted.
  • Extending or renewing resets the warnings.

Idle labs

With the idle policy on, a lab nobody uses is suspended after N days and/or shut down after M days. The two stages are independent; set the default under Settings → Idle labs, and per router on its page (follow the default, own stages, or never). Administrators can exempt single labs.

Counts as useNotes
The owner opening the lab's pageOnce per visit; an open tab refreshing itself doesn't count
The owner viewing credentials, running power or day-2 actions
Extending the lease; Keep runningBy the owner or an administrator
Powering the lab onBy anyone, including the lease renewal
Webtop sessions through the gatewayOwner or administrator
Webtop connections on the routerCounted at every health check; only connections that carried traffic in the last 15 minutes
  • The owner is warned before each stage: a day ahead, or half the stage for stages shorter than two days. The lab page shows "No use seen for … The lab will be suspended / shut down in …" with Keep running.
  • Suspend applies to a running lab. Shut down applies to a running or suspended lab; a suspended lab is resumed first in the same job, because Holodeck signs in to the nested hosts to shut them down.
  • When the shut-down stage comes no later than the suspend stage, the lab is shut down without being suspended first.
  • Expired labs, labs with a job running, and exempt labs are left alone. Every automatic action is audited (lab.idle.suspend, lab.idle.shutdown) and the owner is told.
  • Changing a router's policy, or ending a lab's exemption, starts a fresh idle period.

Jobs and Holodeck

How the portal runs Holodeck, and what to look at when a job misbehaves.

Where jobs run

JobsRunOn a portal restart or update
Lab jobs (deploy, power, day-2, refresh, diagnostics, remove), router checks, configuration jobs (new, settings, precheck)On a Holorouter, in a systemd unit holoportal-remote-job-<id>, started over SSHKeep running; the portal re-attaches and continues mirroring output and forwarding answers
Reading vCenter inventory; deploying, onboarding, detaching and deleting Holorouters; staging installation files (copies stream through the portal)Inside the portal (PowerShell with PowerCLI, SSH)Stop with it (staging resumes where it stopped when started again); updates wait until none is running

How a router job runs

  1. The portal writes a job folder (readable by root only) with the steps and any secrets.
  2. Over SSH it copies its runner to /opt/holodeck-portal-agent/ps/ on the router, sends the job, and starts the unit. The first step copies the Holodeck configuration to the router.
  3. The unit runs PowerShell in a pseudo-terminal, imports Holodeck, deletes the job file and runs each step. Only a fixed list of Holodeck cmdlets and portal helpers is allowed.
  4. The portal mirrors the output to the browser and forwards answers to Holodeck's questions.
  5. When the job ends, however it ends (finished, failed, cancelled, lost), the portal records the result, updates the lab, and removes the files that can hold secrets (job file, prompt answers, raw result) on both sides. The hourly clean-up removes any that are left over. The output log stays.

A job waiting for an answer reminds its owner after 24 hours and is cancelled after 72 (see Settings). If a router can't be reached for 30 minutes, the portal stops waiting (the job may still finish on the router).

Holodeck keeps one global state per router, so jobs that change it run one at a time per router; read-only jobs (diagnostics, checks, inventory, staging) run alongside. A queued job shows "Waiting for the Holodeck lock…".

Unattended Holodeck

The portal always runs New-HoloDeckInstance and the precheck with -DeveloperMode, giving Holodeck the configuration's depot token, proxy, offline depot and placement through environment variables instead of prompts. Anything else Holodeck asks appears as a prompt in the page.

What the portal adds to Holodeck

  • Shut down and power on also handle the VCF Installer / Cloud Builder VM, which Holodeck's own name match misses.
  • Removal deletes VMs Holodeck leaves behind, verifies nothing remains and clears the instance from the configuration.
  • Suspend, force off and power state are read and set directly on vCenter.
  • The portal never edits Holodeck's own files and never runs Reset-HoloRouter or -ResetHoloRouter.

Where to look

# On the appliance
docker logs --tail 200 holodeck-portal                        # the portal
tail -f /data/portal/lib/jobs/<id>/output.log                 # a job's output, as the browser shows it
# On the job's Holorouter
systemctl status holoportal-remote-job-<id>                   # the job's unit
tail -f /var/lib/holodeck-portal-agent/jobs/<id>/output.log   # the job's output there

Security

How the portal protects accounts, secrets, the routers it controls, and itself.

AreaProtection
PasswordsLocal passwords hashed with scrypt; minimum 10 characters. Sign-in attempts are counted before the password is checked: 10 failures per username and address, and 50 per address, in 15 minutes; at most 4 password checks run at once. nginx also limits the sign-in endpoint to 10 requests a minute per address (bursts of 20).
SessionsRandom token in an HttpOnly, SameSite=Lax cookie (Secure over HTTPS); only its hash is stored; 12-hour lifetime. Audit log

Audit log records sign-ins (including failures), sign-outs and password changes, every lab operation, credential views, prompt answers (the question, not the answer), cancels, idle actions and Keep running, user, configuration and settings changes (never secret values), certificate changes, update downloads and installs, and every Holorouter, profile and staging action, with time, user, target, details and IP address. Use the filter box to search.

Known limits

  • Every Holorouter's webtop uses one shared login. Holodeck sets it in its webtop deployment, so the portal can't give each router its own. The default gateway mode (Through the portal only) hides it, uses HTTPS and closes the router's own webtop. On Direct routers lab owners see it, and the link is plain HTTP: choose that only where the lab network is trusted.
  • Every Holorouter OVA also ships the same webtop TLS key and machine-id; the portal replaces only the SSH host keys.
  • Holodeck's own connections to vCenter (every lab job) ignore certificate errors (Holodeck's PowerCLI setting) and carry the vCenter credentials; the configuration, with those credentials, is on every router that runs its jobs.
  • The webtop container runs with extended privileges set by Holodeck; treat anyone with webtop access to a router as able to control that router.
  • The portal's certificate is self-signed until you replace it.

Current limits

  • One lab per Holorouter. Set-HoloRouter configures a router's networks, BGP and DNS for one instance; capacity comes from adding routers.
  • Access is through the lab's webtop. Lab networks aren't routed to users' networks. Every router's webtop uses the same login; the optional webtop gateway hides it.
  • Nested hosts per lab site are capped by Hosts per lab site (default 8) for users.
  • Untagged lab network. Routers sharing one trunk port group share Holodeck's untagged segment, including its DHCP.
  • Single-site labs. Site B networks are reserved for dual-site support.
  • Supervisor and VCF Automation day-2 actions run on one lab at a time.
  • DNS cmdlets. Holodeck's Get/Set/Remove-HoloDeckDNSConfig don't work on 9.1 Holorouters; DNS records are managed in Technitium.
  • No email. Notifications appear in the portal only.
